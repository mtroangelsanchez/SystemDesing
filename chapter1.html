Configuración de Servidor Único

Un viaje de mil millas comienza con un solo paso. Para empezar con algo simple, todo corre en un solo servidor: web app, base de datos, cache, etc.

Figura 1-1

Todo corre en un solo servidor — web app, database y cache

Flujo de Solicitudes

1

DNS Lookup: Los usuarios acceden a sitios web mediante nombres de dominio (api.mysite.com). El DNS es un servicio de pago proporcionado por terceros.

2

IP Address: La dirección IP (ej: 15.125.23.214) es retornada al navegador o app móvil.

3

HTTP Request: Una vez obtenida la IP, las solicitudes HTTP se envían directamente al servidor web.

4

Response: El servidor web retorna páginas HTML o respuestas JSON para renderizado.

Fuentes de Tráfico

🌐 Web Application

  • Server-side: Java, Python, etc.
  • Client-side: HTML, JavaScript
  • Maneja lógica de negocio y storage

📱 Mobile Application

  • Protocolo HTTP para comunicación
  • JSON como formato de respuesta API
  • Simplicidad en transferencia de datos

Base de Datos

Con el crecimiento de la base de usuarios, un solo servidor no es suficiente. Necesitamos separar el tráfico web/mobile (web tier) de la base de datos (data tier) para escalarlos independientemente.

Figura 1-3

Separación de web tier y data tier para escalamiento independiente

¿Qué base de datos usar?

🔗 Relational (SQL)

  • MySQL, PostgreSQL, Oracle
  • Datos en tablas y filas
  • Operaciones JOIN entre tablas
  • 40+ años de historia probada

🔥 Non-Relational (NoSQL)

  • CouchDB, Neo4j, Cassandra, DynamoDB
  • Key-value, Graph, Column, Document
  • No soportan JOIN generalmente
  • Super-low latency, datos no estructurados

💡 ¿Cuándo usar NoSQL?

Tu aplicación requiere super-baja latencia • Datos no estructurados • Solo necesitas serializar/deserializar (JSON, XML, YAML) • Necesitas almacenar cantidades masivas de datos.

Escalamiento Vertical vs Horizontal

⬆️

Vertical Scaling

"Scale Up"

Agregar más poder (CPU, RAM) a tus servidores existentes. Simple pero con límites duros.

↔️

Horizontal Scaling

"Scale Out"

Agregar más servidores a tu pool de recursos. Más deseable para aplicaciones a gran escala.

⚠️ Limitaciones del Vertical Scaling

• Tiene un límite duro — es imposible agregar CPU/memoria ilimitada a un solo servidor.
• No tiene failover ni redundancia — si el servidor cae, todo cae con él.

Balanceador de Carga

Un load balancer distribuye uniformemente el tráfico entrante entre los servidores web definidos en un conjunto balanceado. Los usuarios se conectan a la IP pública del load balancer.

Figura 1-4

Load balancer distribuyendo tráfico entre múltiples servidores con IPs privadas

✓

Failover: Si Server 1 cae, todo el tráfico se redirige a Server 2

✓

Escalabilidad: Solo agrega más servidores al pool cuando el tráfico crece

✓

Seguridad: Servidores web usan IPs privadas, inaccesibles desde internet

Replicación de Base de Datos

La replicación de base de datos usa una relación master/slave. El master soporta operaciones de escritura. Los slaves reciben copias de los datos y solo soportan lecturas.

Figura 1-5

Master database con múltiples slave databases para lecturas distribuidas

✓

Performance: Escrituras en master, lecturas distribuidas en slaves — más queries en paralelo

✓

Reliability: Datos replicados en múltiples ubicaciones — sin pérdida ante desastres

✓

High Availability: El sitio sigue operando incluso si una DB está offline

Caché

Un cache es un área de almacenamiento temporal que guarda resultados de respuestas costosas o datos frecuentemente accedidos en memoria, para que las solicitudes subsecuentes se sirvan más rápido.

Figura 1-7 — Read-through Cache

Estrategia Read-through: verificar cache primero, luego consultar DB si es necesario

Consideraciones del Caché

🎯 Cuándo usar cache

Datos leídos frecuentemente pero modificados infrecuentemente. No ideal para datos persistentes.

⏰ Expiration Policy

No muy corta (recargas frecuentes) ni muy larga (datos obsoletos). Encontrar el balance.

🔄 Consistency

Mantener data store y cache sincronizados. Desafiante en múltiples regiones.

🛡️ Mitigar Failures

Múltiples cache servers en diferentes data centers para evitar SPOF.

🗑️ Eviction Policy

LRU (más popular), LFU, FIFO — cuando el cache está lleno, se eliminan items existentes.

Red de Distribución de Contenido (CDN)

Un CDN es una red de servidores geográficamente dispersos usados para entregar contenido estático. Los servidores CDN cachean contenido estático como imágenes, videos, CSS, JavaScript, etc.

Figura 1-10 — CDN Workflow

CDN workflow: cache en edge servers con TTL, fallback al origin server

Consideraciones del CDN

💰 Costo

CDNs cobran por transferencia de datos. No cachear assets poco usados.

⏱️ Cache Expiry

Ni muy largo (contenido obsoleto) ni muy corto (recargas repetidas del origin).

🔄 CDN Fallback

Clientes deben detectar outages del CDN y solicitar recursos directamente del origin.

🗂️ Invalidación

APIs del vendor para invalidar, o versionado de objetos (image.png?v=2).

Capa Web Sin Estado

Para escalar horizontalmente el web tier, necesitamos mover el estado (session data) fuera del web tier a un almacenamiento persistente compartido.

🔒

Stateful

Sticky Sessions

Cada request del mismo cliente debe ir al mismo servidor. Difícil agregar/remover servidores.

🔓

Stateless

Shared Data Store

Requests pueden ir a cualquier servidor. Estado en Redis/Memcached/NoSQL. Auto-scaling fácil.

🎯 Shared Data Store

NoSQL es la opción elegida por su facilidad de escalamiento. Autoscaling = agregar o remover servidores automáticamente basado en la carga de tráfico.

Centros de Datos

Para mejorar la disponibilidad y experiencia de usuario globalmente, soportar múltiples data centers es crucial. Los usuarios son geo-routed al data center más cercano.

Figura 1-15 — Multi Data Center

Multi data center con GeoDNS routing y sincronización de datos

Cola de Mensajes

Una message queue es un componente durable que soporta comunicación asíncrona. Sirve como buffer y distribuye requests asíncronos.

Figura 1-18 — Photo Processing Queue

Desacoplamiento con message queue — producers y consumers escalan independientemente

🔑 Ventaja del Desacoplamiento

El producer puede publicar mensajes cuando el consumer no está disponible. El consumer puede leer mensajes cuando el producer no está disponible. Escalamiento independiente según la carga.

Escalamiento de Base de Datos — Sharding

Sharding separa bases de datos grandes en partes más pequeñas y manejables llamadas shards. Cada shard comparte el mismo schema pero los datos son únicos por shard.

Figura 1-21 — Sharded Databases

Datos distribuidos en shards usando hash function sobre user_id

Desafíos del Sharding

🔄 Redistribución

Necesario cuando un shard no puede contener más datos. El hashing consistente resuelve esto.

🌟 Problema de Celebridades

Clave caliente — acceso excesivo a un shard específico. Solución: shard dedicado por celebridad.

🔗 Join y Desnormalización

Difícil hacer JOINs entre shards. Solución: desnormalizar para consultas en una sola tabla.

Registros, Métricas y Automatización

📊

Registros: Monitorear logs de errores a nivel de servidor o agregar a un servicio centralizado

📈

Métricas: Nivel de host (CPU, Memoria), Agregado (capa de BD, capa de Caché), Negocio (DAU, Ingresos)

🤖

Automatización: CI/CD, build/test/deploy automatizado para mejorar productividad

Mejores Prácticas por Componente

⚖️ Balanceador de Carga — Mejores Prácticas

• Usar balanceadores de capa 7 (Application) para enrutamiento basado en contenido (path, headers, host)
• Implementar health checks activos con intervalos cortos para detectar fallos rápidamente
• Habilitar connection draining para terminar conexiones existentes de forma elegante
• AWS: ALB con target groups + WAF integrado
• GCP: Global HTTP(S) Load Balancer con Cloud Armor
• Azure: Application Gateway con WAF v2

⚡ Caché — Mejores Prácticas

• Implementar patrón Cache-Aside (lazy loading) para la mayoría de casos de uso
• Usar TTL adaptativo: más corto para datos volátiles, más largo para datos estables
• Configurar cluster mode con réplicas de lectura para alta disponibilidad
• AWS: ElastiCache Redis con Multi-AZ y cifrado en tránsito
• GCP: Memorystore con failover automático entre zonas
• Azure: Azure Cache for Redis Premium con persistencia RDB/AOF

🗄️ Base de Datos — Mejores Prácticas

• Usar read replicas para distribuir carga de lectura (ratio típico 80% lectura / 20% escritura)
• Implementar connection pooling para reducir overhead de conexiones
• Automatizar backups con point-in-time recovery
• AWS: Aurora con hasta 15 réplicas de lectura + Global Database para multi-región
• GCP: Cloud Spanner para escala global con consistencia fuerte
• Azure: Cosmos DB con distribución multi-región y 5 modelos de consistencia

Arquitecturas AWS con Terraform

A continuación se presentan las configuraciones de Terraform para implementar cada capa de la arquitectura descrita en este ejemplo. Cada bloque es incremental — construimos desde la red base hasta la aplicación completa.

1. Red Base — VPC, Subnets y Security Groups

🌐 Fundamento de Red

Toda arquitectura escalable comienza con una VPC bien diseñada. Usamos subnets públicas para el balanceador y subnets privadas para servidores y bases de datos. Esto garantiza que los componentes internos nunca sean accesibles directamente desde internet.

# provider.tf — Configuración del proveedor AWS terraform { required_providers { aws = { source = "hashicorp/aws" version = "~> 5.0" } } } provider "aws" { region = "us-east-1" }
# vpc.tf — VPC con subnets públicas y privadas resource "aws_vpc" "main" { cidr_block = "10.0.0.0/16" enable_dns_hostnames = true enable_dns_support = true tags = { Name = "system-design-vpc" } } resource "aws_subnet" "public_a" { vpc_id = aws_vpc.main.id cidr_block = "10.0.1.0/24" availability_zone = "us-east-1a" map_public_ip_on_launch = true tags = { Name = "public-subnet-a" } } resource "aws_subnet" "public_b" { vpc_id = aws_vpc.main.id cidr_block = "10.0.2.0/24" availability_zone = "us-east-1b" map_public_ip_on_launch = true tags = { Name = "public-subnet-b" } } resource "aws_subnet" "private_a" { vpc_id = aws_vpc.main.id cidr_block = "10.0.10.0/24" availability_zone = "us-east-1a" tags = { Name = "private-subnet-a" } } resource "aws_subnet" "private_b" { vpc_id = aws_vpc.main.id cidr_block = "10.0.11.0/24" availability_zone = "us-east-1b" tags = { Name = "private-subnet-b" } }

2. Balanceador de Carga — Application Load Balancer

⚖️ ALB con Health Checks

El ALB distribuye tráfico entre múltiples instancias en diferentes zonas de disponibilidad. Los health checks verifican que cada instancia responda correctamente antes de enviarle tráfico.

# alb.tf — Application Load Balancer resource "aws_lb" "app" { name = "app-alb" internal = false load_balancer_type = "application" security_groups = [aws_security_group.alb_sg.id] subnets = [aws_subnet.public_a.id, aws_subnet.public_b.id] tags = { Name = "app-load-balancer" } } resource "aws_lb_target_group" "app" { name = "app-tg" port = 80 protocol = "HTTP" vpc_id = aws_vpc.main.id health_check { path = "/health" healthy_threshold = 2 unhealthy_threshold = 3 timeout = 5 interval = 30 } } resource "aws_lb_listener" "http" { load_balancer_arn = aws_lb.app.arn port = 80 protocol = "HTTP" default_action { type = "forward" target_group_arn = aws_lb_target_group.app.arn } }

3. Auto Scaling — Servidores Web Stateless

📈 Escalamiento Automático

El Auto Scaling Group mantiene entre 2 y 10 instancias según la carga de CPU. Las instancias son stateless — toda la sesión se almacena en ElastiCache Redis.

# asg.tf — Auto Scaling Group con Launch Template resource "aws_launch_template" "app" { name_prefix = "app-server-" image_id = "ami-0c02fb55956c7d316" # Amazon Linux 2023 instance_type = "t3.medium" network_interfaces { security_groups = [aws_security_group.app_sg.id] associate_public_ip_address = false } user_data = base64encode(<<-EOF #!/bin/bash yum update -y yum install -y docker systemctl start docker docker pull myapp:latest docker run -d -p 80:8080 myapp:latest EOF ) tag_specifications { resource_type = "instance" tags = { Name = "app-server" } } } resource "aws_autoscaling_group" "app" { name = "app-asg" desired_capacity = 2 min_size = 2 max_size = 10 target_group_arns = [aws_lb_target_group.app.arn] vpc_zone_identifier = [aws_subnet.private_a.id, aws_subnet.private_b.id] launch_template { id = aws_launch_template.app.id version = "$Latest" } } # Política de escalamiento por CPU resource "aws_autoscaling_policy" "cpu" { name = "cpu-target-tracking" autoscaling_group_name = aws_autoscaling_group.app.name policy_type = "TargetTrackingScaling" target_tracking_configuration { predefined_metric_specification { predefined_metric_type = "ASGAverageCPUUtilization" } target_value = 60.0 } }

4. Base de Datos — Aurora con Réplicas de Lectura

🗄️ Aurora MySQL Multi-AZ

Aurora proporciona replicación automática con hasta 15 réplicas de lectura, failover automático en menos de 30 segundos y almacenamiento que escala automáticamente hasta 128 TB.

# aurora.tf — Cluster Aurora con réplicas de lectura resource "aws_rds_cluster" "main" { cluster_identifier = "app-aurora-cluster" engine = "aurora-mysql" engine_version = "8.0.mysql_aurora.3.04.0" database_name = "appdb" master_username = "admin" master_password = var.db_password # Usar AWS Secrets Manager vpc_security_group_ids = [aws_security_group.db_sg.id] db_subnet_group_name = aws_db_subnet_group.main.name backup_retention_period = 7 preferred_backup_window = "03:00-04:00" skip_final_snapshot = false } # Instancia Writer (Master) resource "aws_rds_cluster_instance" "writer" { identifier = "app-aurora-writer" cluster_identifier = aws_rds_cluster.main.id instance_class = "db.r6g.large" engine = aws_rds_cluster.main.engine } # Instancias Reader (Slaves) — 2 réplicas resource "aws_rds_cluster_instance" "readers" { count = 2 identifier = "app-aurora-reader-${count.index}" cluster_identifier = aws_rds_cluster.main.id instance_class = "db.r6g.large" engine = aws_rds_cluster.main.engine }

5. Caché — ElastiCache Redis Cluster

# elasticache.tf — Redis con réplicas Multi-AZ resource "aws_elasticache_replication_group" "redis" { replication_group_id = "app-redis" description = "Redis cache para sesiones y datos frecuentes" node_type = "cache.r6g.large" num_cache_clusters = 3 # 1 primario + 2 réplicas engine_version = "7.0" port = 6379 automatic_failover_enabled = true multi_az_enabled = true at_rest_encryption_enabled = true transit_encryption_enabled = true subnet_group_name = aws_elasticache_subnet_group.main.name security_group_ids = [aws_security_group.redis_sg.id] }

6. CDN y Almacenamiento Estático — CloudFront + S3

# cdn.tf — CloudFront + S3 para assets estáticos resource "aws_s3_bucket" "static" { bucket = "app-static-assets-${random_id.suffix.hex}" tags = { Name = "static-assets" } } resource "aws_s3_bucket_versioning" "static" { bucket = aws_s3_bucket.static.id versioning_configuration { status = "Enabled" } } resource "aws_cloudfront_distribution" "cdn" { origin { domain_name = aws_s3_bucket.static.bucket_regional_domain_name origin_id = "s3-static" s3_origin_config { origin_access_identity = aws_cloudfront_origin_access_identity.oai.cloudfront_access_identity_path } } enabled = true default_root_object = "index.html" default_cache_behavior { allowed_methods = ["GET", "HEAD"] cached_methods = ["GET", "HEAD"] target_origin_id = "s3-static" viewer_protocol_policy = "redirect-to-https" forwarded_values { query_string = false cookies { forward = "none" } } min_ttl = 0 default_ttl = 86400 # 24 horas max_ttl = 604800 # 7 días } restrictions { geo_restriction { restriction_type = "none" } } viewer_certificate { cloudfront_default_certificate = true } }

7. Cola de Mensajes — SQS + Lambda Workers

# sqs.tf — Cola SQS con Dead Letter Queue resource "aws_sqs_queue" "tasks" { name = "app-task-queue" visibility_timeout_seconds = 300 message_retention_seconds = 1209600 # 14 días receive_wait_time_seconds = 20 # Long polling redrive_policy = jsonencode({ deadLetterTargetArn = aws_sqs_queue.dlq.arn maxReceiveCount = 3 }) } resource "aws_sqs_queue" "dlq" { name = "app-task-queue-dlq" } # Lambda como worker/consumer resource "aws_lambda_function" "worker" { function_name = "task-worker" runtime = "python3.12" handler = "handler.process" filename = "worker.zip" role = aws_iam_role.lambda_role.arn timeout = 300 memory_size = 512 } resource "aws_lambda_event_source_mapping" "sqs_trigger" { event_source_arn = aws_sqs_queue.tasks.arn function_name = aws_lambda_function.worker.arn batch_size = 10 }

nginx.conf — Balanceador de Carga

# nginx/nginx.conf events { worker_connections 1024; } http { # Upstream: grupo de servidores de aplicación upstream app_servers { least_conn; # Enviar al servidor con menos conexiones server app1:3000; server app2:3000; } server { listen 80; # Health check endpoint location /health { access_log off; return 200 "OK"; } # Proxy a los servidores de aplicación location / { proxy_pass http://app_servers; proxy_set_header Host $host; proxy_set_header X-Real-IP $remote_addr; proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for; proxy_connect_timeout 5s; proxy_read_timeout 30s; } # Assets estáticos servidos directamente location /static/ { alias /usr/share/nginx/html/static/; expires 7d; add_header Cache-Control "public, immutable"; } } }

server.js — Aplicación con Caché y Replicación

// app/server.js const express = require('express'); const Redis = require('ioredis'); const { Pool } = require('pg'); const amqp = require('amqplib'); const app = express(); app.use(express.json()); // Conexión a Redis (Caché + Sesiones) const redis = new Redis(process.env.REDIS_URL); // Pool de conexiones — Master para escrituras const writePool = new Pool({ host: process.env.DB_WRITE_HOST, database: process.env.DB_NAME, user: 'admin', password: process.env.DB_PASSWORD, max: 20 }); // Pool de conexiones — Réplica para lecturas const readPool = new Pool({ host: process.env.DB_READ_HOST, database: process.env.DB_NAME, user: 'admin', password: process.env.DB_PASSWORD, max: 20 }); // GET /users/:id — Read-through cache app.get('/users/:id', async (req, res) => { const { id } = req.params; // 1. Verificar caché const cached = await redis.get(`user:${id}`); if (cached) return res.json(JSON.parse(cached)); // 2. Cache miss → leer de réplica const { rows } = await readPool.query( 'SELECT * FROM users WHERE id = $1', [id] ); if (rows.length === 0) return res.status(404).json({ error: 'No encontrado' }); // 3. Guardar en caché (TTL: 5 minutos) await redis.setex(`user:${id}`, 300, JSON.stringify(rows[0])); res.json(rows[0]); }); // POST /users — Escribir en master + invalidar caché app.post('/users', async (req, res) => { const { name, email } = req.body; const { rows } = await writePool.query( 'INSERT INTO users (name, email) VALUES ($1, $2) RETURNING *', [name, email] ); // Publicar tarea asíncrona en la cola const channel = await getChannel(); channel.sendToQueue('tasks', Buffer.from(JSON.stringify({ type: 'welcome_email', userId: rows[0].id }))); res.status(201).json(rows[0]); }); app.get('/health', (req, res) => res.json({ status: 'ok' })); app.listen(3000, () => console.log('Servidor en puerto 3000'));

worker.js — Consumer de la Cola

// app/worker.js — Procesa tareas de la cola const amqp = require('amqplib'); async function startWorker() { const conn = await amqp.connect(process.env.RABBITMQ_URL); const channel = await conn.createChannel(); await channel.assertQueue('tasks', { durable: true }); channel.prefetch(5); // Procesar 5 mensajes a la vez console.log('Worker esperando tareas...'); channel.consume('tasks', async (msg) => { const task = JSON.parse(msg.content.toString()); console.log(`Procesando: ${task.type} para usuario ${task.userId}`); try { switch (task.type) { case 'welcome_email': await sendWelcomeEmail(task.userId); break; case 'process_image': await processImage(task.imageUrl); break; } channel.ack(msg); // Confirmar procesamiento exitoso } catch (error) { console.error('Error:', error); channel.nack(msg, false, true); // Reintentar } }); } startWorker();

Comandos para Ejecutar

1

Levantar todo: docker compose up -d --build — Construye imágenes y levanta todos los servicios en segundo plano.

2

Ver logs: docker compose logs -f app1 app2 worker — Monitorear la aplicación y el worker en tiempo real.

3

Probar balanceo: for i in $(seq 1 10); do curl http://localhost/health; done — Verás respuestas alternando entre app1 y app2.

4

Escalar: docker compose up -d --scale app1=3 — Agregar más instancias de la app dinámicamente.

5

Panel RabbitMQ: Abrir http://localhost:15672 (admin/rabbitpass) para ver la cola de mensajes visualmente.

6

Detener todo: docker compose down -v — Detiene contenedores y elimina volúmenes.

💡 ¿Qué demuestra este ejemplo?

Este docker-compose replica localmente todos los conceptos del capítulo:
• Balanceador de carga: Nginx con upstream round-robin
• Servidores stateless: 2+ instancias de la app sin estado local
• Caché read-through: Redis con TTL de 5 minutos
• Replicación de BD: PostgreSQL master (escrituras) + réplica (lecturas)
• Cola de mensajes: RabbitMQ con worker consumer independiente
• Escalamiento horizontal: docker compose --scale para agregar instancias
